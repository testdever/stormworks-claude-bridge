  見張りが最初の値を待つ時間が3秒と短すぎた。→ 最初の値は15秒まで待つように直した（値が届き始めたあとは、3秒途切れたら止める）。

  原因は分からない。2026-11-03（この取り組みの前）にも crashes フォルダに記録があった。
  確かめ方：Claude Bridge を有効にしたワールドと、していないワールドで、終了時に落ちるかを比べる。

## ゲームが落ちた件の読み取り（2026-11-09）

本人のPCのクラッシュの記録（`%APPDATA%\Stormworks\crashes\` の json・log）を2件読んだ。
記録には Steam ID などが入っているので、リポジトリには入れていない。

| | 1件目 | 2件目 |
|---|---|---|
| 時刻（UTC / 日本時間） | 2026-11-08 12:29:31 / 21:29 | 2026-11-09 08:19:28 / 17:19 |
| 落ちたスレッド | **http** | **http** |
| 内容 | STATUS_HEAP_CORRUPTION（ntdll.dll の RtlpMuiRegCreateRegistryInfo） | 同じ |
| 起動からの時間 | 770 秒 | 136 秒（ログでは 129 秒でメニューに戻り、その7秒後） |
| 直前 | Q3（21:19 開始）が終わって約10分後 | Q6（17:19 開始）が4秒で止まった約2分後 |

- 実測：2件とも、ゲームの HTTP を扱うスレッドで落ちた。2件とも、中継プログラムを閉じたあと、アドオン（とマイコン）が動いたままの時間があった。
- 推論：中継プログラムが閉じている間、アドオンとマイコンは返事を待ちきれず送り直し、ゲームはその要求を捨てずに溜める（Q2 で確かめた）。
  その状態でワールドを抜けると、溜まった要求の後始末で HTTP の処理が壊れるのではないか。ゲーム側の不具合と見られる。
- 確かめ方：実験のあと `python relay.py --seconds 0`（止まらずに返事を返し続ける）を動かしたままワールドを抜け、落ちるかを見る。
  落ちなければ、溜まった要求が原因。アドオンとマイコンを、返事がない間は送り直しの間隔を伸ばして溜めない作りにする。

## 2026-11-09 18:01 ゲームを終了しても落ちるか（返事を返し続けた場合）

- Q6 が終わった直後に `python relay/relay.py --seconds 0`（止まらずに返事を返し続ける）を起動し、その間に本人がワールドを抜けてゲームを終了した。

- 推論：返事のない間にアドオンとマイコンが送る要求が溜まることが、落ちる原因の見込みが高い。ただし、落ちなかったのはまだ1回だけ。
